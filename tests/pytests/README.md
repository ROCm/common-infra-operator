# Pytest Validation Framework

End-to-end validation tests for the AMD GPU Operator stack. Tests cover
gpu-operator, device-metrics-exporter (DME), device-config-manager (DCM),
and kernel-module-management (KMM) across Kubernetes, OpenShift, standalone,
and hypervisor deployment targets.

## Prerequisites

- Python 3.8+
- Image manifest YAML (generated by `ci-internal/gen_image_manifest.py`)
- Helm 3.x (downloaded automatically by the launcher scripts)

### Target-Specific Prerequisites

| Target | Required |
|--------|----------|
| k8 | `kubeconfig` — configured via `~/.kube/config` or `KUBECONFIG` env var |
| openshift | `kubeconfig` — configured via `~/.kube/config` or `KUBECONFIG` env var; `oc` CLI |
| standalone | `--testbed` JSON — provides SSH credentials to the bare-metal host |
| hypervisor | `--testbed` JSON — provides SSH credentials and VM configuration |

### Environment Setup

```bash
cd tests/pytests
./scripts/prepare_env.sh ./venv
source venv/bin/activate
```

This installs all Python dependencies from `scripts/requirements.txt`:
fabric, pytest, pytest-html, ruamel.yaml, kubernetes, prometheus_client, etc.

## Generating the Image Manifest

Before running any tests, generate the image manifest using
`ci-internal/gen_image_manifest.py`. The script reads a scenario config,
downloads helm charts and debian packages, and writes
`tests/pytests/images.yaml`.

```bash
# From the repo root:

# Nightly — DME + DCM against today's ROCm nightly
python3 ci-internal/gen_image_manifest.py ci-internal/nightly-dme-dcm.yaml

# Nightly — specific date, specific target
python3 ci-internal/gen_image_manifest.py ci-internal/nightly-dme-dcm.yaml \
    --date 20260923 --target standalone

# Pre-release — DME + DCM against ROCm 10.1.0 (auto-detects latest RC)
python3 ci-internal/gen_image_manifest.py ci-internal/prerelease-10.1.0.yaml
```

See `ci-internal/README.md` for the full manifest generator documentation.

## DME and DCM Operand Sanity

When releasing DME or DCM against a new ROCm version, the following tests
are the required sanity suite. These use `--module` to run only the
component-specific test file within the `gpu-operator` app.

`--module` maps to `test_{module}.py` and `--testcase` maps to
`test_{testcase}()` within that file.

### DME (Device Metrics Exporter) Sanity

#### Exporter — K8s with DeviceConfig driver

Validates DME deployment, NodePort/ClusterIP service types, RBAC, mTLS,
ServiceMonitor, pod/service annotations, and metrics endpoint.

```bash
# Generate manifest with the DME build to validate
python3 ci-internal/gen_image_manifest.py ci-internal/prerelease-10.1.0.yaml

cd tests/pytests
./k8_test_launcher.sh \
    --app gpu-operator \
    --image-manifest images.yaml \
    --amdgpu-driver-spec lib/files/amd-deviceconfig-default-driver-spec.json \
    --module metrics_exporter
```

Test cases in `test_metrics_exporter.py`:
- `test_exporter_nodeport_deploy` — basic DME deployment with NodePort
- `test_exporter_nodeport_rbac_support` — RBAC token-based auth
- `test_exporter_nodeport_rbac_http` — RBAC over HTTP
- `test_exporter_nodeport_exp_config` — exporter ConfigMap customization
- `test_exporter_clusterip_rbac_internal_port` — ClusterIP with internal port
- `test_exporter_servicemonitor_enable_flag` — Prometheus ServiceMonitor
- `test_exporter_pod_annotations` / `test_exporter_service_annotations`
- `test_exporter_rbac_mTLS_cert_support` — mutual TLS
- `test_exporter_operand_upgrade` — DME rolling upgrade

#### Metrics Values — validation of reported GPU metrics

```bash
./k8_test_launcher.sh \
    --app gpu-operator \
    --image-manifest images.yaml \
    --amdgpu-driver-spec lib/files/amd-deviceconfig-default-driver-spec.json \
    --module metrics_values
```

Test cases in `test_metrics_values.py`:
- `test_exporter_all_supported_metrics` — all metrics are exposed
- `test_exporter_metrics_completeness` — per-metric completeness check
- `test_exporter_metrics_value_accuracy` — metric values match sysfs/rocm-smi
- `test_metric_coverage` — no gaps in metric catalog

#### Test Runner — health check and diagnostics framework

```bash
./k8_test_launcher.sh \
    --app gpu-operator \
    --image-manifest images.yaml \
```

- `test_deviceconfig_test_runner_deploy` — test-runner pod lifecycle

- `test_manual_job` / `test_pre_job` — on-demand and pre-workload jobs
- `test_test_runner_rolling_update` — test-runner rolling upgrade

### DCM (Device Config Manager) Sanity

#### Config Manager — K8s with DeviceConfig driver

Validates DCM deployment, GPU partitioning (CDNA only), and config
lifecycle.

```bash
python3 ci-internal/gen_image_manifest.py ci-internal/prerelease-10.1.0.yaml

cd tests/pytests
./k8_test_launcher.sh \
    --app gpu-operator \
    --image-manifest images.yaml \
    --amdgpu-driver-spec lib/files/amd-deviceconfig-default-driver-spec.json \
    --module config_manager
```

Test cases in `test_config_manager.py`:
- `test_deviceconfig_config_manager_deploy` — DCM pod lifecycle
- `test_negative_partitioning` — invalid partition spec handling
- `test_partitioning_no_workload_MI300X` / `MI325X` / `MI350X` / `MI350P` — idle partitioning per GPU
- `test_partitioning_workload_MI300X` / `MI325X` / `MI350X` / `MI350P` — partitioning under workload
- `test_partitioning_test_runner` — partitioning with test-runner active
- `test_config_manager_operand_upgrade` — DCM rolling upgrade
- `test_deviceconfig_config_manager_disable` — disable/enable DCM

> **Note:** Partitioning tests (`test_partitioning_*`) require CDNA-architecture
> GPUs (MI300X, MI325X, MI350X, MI350P) and are marked with the
> `config_manager` pytest marker. They are skipped on non-CDNA hardware.

## AMDGPU Driver Selection

The `--amdgpu-driver-spec` argument controls how the AMDGPU driver is
handled during tests. It points to a JSON spec file that declares the
driver deployment mode and version.

### Inbox Driver (QA Validation)

The primary workflow for AMD QA validation uses **inbox driver** — the
AMDGPU driver is pre-installed on the test infrastructure and managed
outside of the gpu-operator. Tests that require operator-managed driver
deployment (install, upgrade, source-image builds) are automatically
skipped when inbox mode is selected.

```bash
# QA validation — inbox driver, DME exporter sanity
./k8_test_launcher.sh \
    --app gpu-operator \
    --image-manifest images.yaml \
    --amdgpu-driver-spec lib/files/amd-inbox-driver-spec.json \
    --module metrics_exporter

# QA validation — inbox driver, DCM config manager sanity
./k8_test_launcher.sh \
    --app gpu-operator \
    --image-manifest images.yaml \
    --amdgpu-driver-spec lib/files/amd-inbox-driver-spec.json \
    --module config_manager

# QA validation — inbox driver, test runner sanity
./k8_test_launcher.sh \
    --app gpu-operator \
    --image-manifest images.yaml \
    --amdgpu-driver-spec lib/files/amd-inbox-driver-spec.json \
    --module test_runner

# QA validation — inbox driver, DME helm chart only
./k8_test_launcher.sh \
    --app gpu-operator-exporter \
    --image-manifest images.yaml \
    --amdgpu-driver-spec lib/files/amd-inbox-driver-spec.json
```

### DeviceConfig Driver (Operator-Managed)

For full operator sanity where the gpu-operator manages driver installation
via DeviceConfig CRs:

```bash
# Default — latest deviceconfig driver
./k8_test_launcher.sh \
    --app gpu-operator \
    --image-manifest images.yaml \
    --amdgpu-driver-spec lib/files/amd-deviceconfig-default-driver-spec.json

# Pin to specific driver version for regression
./k8_test_launcher.sh \
    --app gpu-operator \
    --image-manifest images.yaml \
    --amdgpu-driver-spec lib/files/amd-deviceconfig-driver-spec-31.40.1.json
```

### Driver Modes Summary

| Mode | Spec File | Use Case |
|------|-----------|----------|
| Inbox | `lib/files/amd-inbox-driver-spec.json` | QA validation — driver pre-installed on infra, skips driver lifecycle tests |
| DeviceConfig (default) | `lib/files/amd-deviceconfig-default-driver-spec.json` | Full operator sanity — driver managed by gpu-operator via DeviceConfig CR |
| Specific version | `lib/files/amd-deviceconfig-driver-spec-{version}.json` | Regression — pin to a specific driver version |

### Driver Spec JSON Format

```json
{
    "driver-deployment": "inbox",
    "default-version": "31.50"
}
```

```json
{
    "driver-deployment": "deviceconfig",
    "default-version": "31.50",
    "alternative-versions": ["30.20.1", "30.30", "31.40.1", "31.40"],
    "source-image-versions": ["31.40.1", "31.50"]
}
```

- `driver-deployment` — `"inbox"` (pre-installed, skip driver tests) or `"deviceconfig"` (operator-managed)
- `default-version` — driver version on the system (inbox) or version to install (deviceconfig)
- `alternative-versions` — versions tested during driver upgrade/downgrade (deviceconfig only)
- `source-image-versions` — versions with pre-built source images for KMM (deviceconfig only)

## Testbed JSON

The `--testbed` argument points to a JSON file describing the target host.
It is **required for standalone and hypervisor** targets (provides SSH
credentials to the host/VM). It is **not needed for k8 and openshift**
targets where kubeconfig is pre-configured.

When provided, the testbed supplies:

- SSH credentials to the target host
- Deployment type (`standalone`, `hypervisor`)
- GPU platform properties (series, count, architecture)
- Node information (hostnames, IPs)
- VM configuration (hypervisor only)

Testbed files are environment-specific and not committed to the repository.
